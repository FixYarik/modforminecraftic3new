# Архитектура Industrial Evolution

Целевая платформа: Minecraft Java Edition 1.20.1, Minecraft Forge 47.3.0,
Java 17. Идентификатор мода — `industrialevolution`, корневой Java-пакет —
`com.industrialevolution`. ForgeGradle использует официальные имена Minecraft.

Проект развивается по восьми собираемым этапам. Первый этап содержит
регистрацию мода, творческую вкладку, резину и корпус механизма. Это готовые
компоненты будущей технологической цепочки; механизмы и EU появляются на
следующих этапах. Статус фактических проверок сборки указан в README.

## Реализованные классы

| Файл в `src/main/java/com/industrialevolution/` | Ответственность |
| --- | --- |
| `IndustrialEvolution.java` | Общая точка входа `@Mod`, константа `MOD_ID`, подключение регистров к шине событий мода. |
| `registry/ModBlocks.java` | `DeferredRegister<Block>` и корпус `industrialevolution:machine_casing`. |
| `registry/ModItems.java` | `DeferredRegister<Item>`, резина `industrialevolution:rubber` и `BlockItem` корпуса. |
| `registry/ModCreativeTabs.java` | Творческая вкладка `industrialevolution:main`, её иконка, заголовок и содержимое. |

`DeferredRegister` передаёт создание объектов жизненному циклу Forge.
Связь между блоком и его предметом задаётся через `RegistryObject` внутри
поставщика `BlockItem`, а не через преждевременное создание экземпляров.
Точка входа только подключает регистры; игровая логика будет находиться
в соответствующих модулях.

Все четыре класса используют общий API. Они не импортируют
`net.minecraft.client` и не выполняют клиентскую инициализацию: один JAR
предназначен для клиента и выделенного сервера. Творческая вкладка также
регистрируется общим API Forge. Проверка фактической серверной загрузки
выполняется отдельно от компиляции.

## Ресурсы и выживание

`src/main/resources/assets/industrialevolution` содержит модели, состояние
блока, локализации `en_us`/`ru_ru` и четыре оригинальные текстуры 16×16.
Текстуры и JSON воспроизводятся командой `python3 tools/generate_assets.py`;
скрипту достаточно стандартной библиотеки Python.

`src/main/resources/data` содержит рецепты, достижения для открытия рецептов,
таблицу добычи и теги. На первом этапе доступна самостоятельная цепочка:

1. Шарик слизи + сушёная ламинария → 2 резины, бесформенный рецепт.
2. Восемь железных слитков вокруг резины → корпус механизма.
3. Установленный корпус добывается каменной киркой или лучше и возвращается
   предметом, если соблюдены условия добычи.

Это осознанный стартовый путь выживания из ванильных ресурсов. Будущее
извлечение резины из смолы дополнит этот путь промышленной переработкой.
Рецепт корпуса принимает `forge:ingots/iron` и `forge:rubber`; наш предмет
включён в `forge:rubber`. Корпус отмечен тегами `minecraft:mineable/pickaxe`
и `minecraft:needs_stone_tool`. Рецепты хранятся в datapack-формате и могут
быть переопределены сборкой модов.

## Направление развития модулей

Следующие пакеты запланированы; их реализаций на первом этапе нет.
Пустые классы и фиктивные механизмы для них не создаются.

| Пакет | Будущая ответственность и границы |
| --- | --- |
| `energy` | EU API, уровни напряжения, хранилища, передача, потери, перегрузки и настройки разрушений. Forge Energy подключается только через явный преобразователь. |
| `machine` | `BlockEntity` механизмов, инвентари, сохранение NBT, обработка операций и серверный тик. |
| `recipe` | Типы и сериализаторы производственных рецептов; входы, выходы, длительность и стоимость EU. |
| `gui` | Общие меню и их синхронизация; экраны выделяются в клиентский подпакет и регистрируются только на стороне клиента. |
| `reactor` | Условная игровая тепловая модель, компоненты реактора и аварийное отключение. |
| `network` | Промышленная сеть, пакеты синхронизации и команды с проверкой на сервере. |
| `automation` | Стороны ввода/вывода, улучшения, транспорт, фильтры, сортировка и автоматическая добыча. |
| `worldgen` | Генерация руд и связанные определения ресурсов и биомов. |
| `integration` | Отдельные необязательные интеграции JEI, Jade и внешних API. |

Сервер будет владеть энергией, инвентарём, ходом обработки и изменениями
мира. Клиентские экраны будут отображать синхронизированные данные и
отправлять проверяемые запросы. Сохранённое состояние не должно зависеть
от наличия открытого интерфейса. Для автоматизации планируется использовать
Forge capabilities с явными правилами доступа по сторонам блока.

## Проверки

Gradle собирает основной мод и отдельный source set `gametest`.
Игровые проверки находятся в `src/gametest` и не включаются в основной JAR.
Они предназначены для проверки зарегистрированного контента и ресурсов
в работающей среде Minecraft. Наличие тестов не означает, что они уже
успешно выполнены: результаты запуска фиксируются отдельно.

На следующих этапах появятся изолированные тесты энергетических расчётов,
производственных рецептов и игровых сценариев сохранения и автоматизации.
Клиентские модели, переводы, масштабирование и интерфейсы также потребуют
визуальной проверки в игре.
